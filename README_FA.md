# اپلیکیشن Native Android بازرسی — رابط کاربری رسمی نسخه ۰.۴

**تغییرات نسخه ۰.۴:** هدر رسمی مشترک با صفحه ورود سایت (به‌صورت تصویر WebP بومی در اپ)، رنگ سازمانی سرمه‌ای/طلایی، آیکون‌های برجسته با قاب دو‌رنگ، کارت‌های سفید با حاشیه ظریف، ناوبری پایین با حالت انتخاب واضح و صفحه ورود ساده‌تر. مسیرهای API، سطح دسترسی و منطق ذخیره آفلاین تغییر نکرده است. این برنامه همچنان Native است و WebView نیست.

**مهم:** این نسخه سورس است؛ APK واقعی در این محیط ساخته یا روی گوشی تست نشده است. برای بررسی عملی باید با Android SDK 35 و Gradle ساخته شود. تصویر بنر به‌عنوان drawable-nodpi داخل خود برنامه قرار گرفته و برای نمایش آن اینترنت لازم نیست.

**جدید:** رابط کاربری چهار تب، صفحه خانه بازرس، فهرست پیش‌نویس‌ها، چک‌لیست مرحله‌ای، ذخیره خودکار و آیکون جدید. جزئیات در فایل `../UPGRADE_INSPECTOR_UI_FA.md` آمده است.

# اپلیکیشن Native Android بازرسی — مرحله ۲

این پروژه یک اپلیکیشن **Android/Kotlin** است، نه WebView. هدف آن ایجاد کلاینت اندروید قابل توسعه بر پایه API موجود و فعال‌سازی احراز هویت امن است.

## راه‌اندازی با Android Studio یا GitHub

1. پوشه `android-native` را در Android Studio باز کنید. JDK 17 و Android SDK 35 لازم است؛ Gradle 8.13 و Android Gradle Plugin 8.9.2 برای پروژه تعریف شده‌اند.
2. آدرس واقعی HTTPS سامانه را در فایل **محلی** `~/.gradle/gradle.properties` بگذارید:

   `BAZR_API_BASE_URL=https://staging.example.org/api/`

3. ابتدا API مرحله ۲ را در سرور آزمایشی نصب و `mobile_activate_authenticated.php` را بررسی کنید.
4. برای ساخت در Android Studio گزینه Build > Build APK(s) را انتخاب کنید؛ یا با نصب Gradle 8.13 دستور `gradle :app:assembleDebug` اجرا کنید.
5. برای GitHub سورس را با پوشه `android-native` داخل مخزن نگه دارید. اکشن نمونه در `.github/workflows/android.yml` این پوشه نیز موجود است؛ برای اجرای اکشن، فایل workflow را به `.github/workflows/android.yml` در ریشه مخزن منتقل کنید.

**هیچ APK در این مرحله تولید یا روی دستگاه واقعی آزمایش نشده است؛ نتیجه build فقط با Android SDK/Gradle و اتصال به مخازن وابستگی قابل تأیید است.** مقدار `example.invalid` فقط نشانگر است و باید جایگزین شود.

## جریان احراز هویت

1. بازرس به `login.php` با `kind=inspector` وارد می‌شود.
2. توکن وب فقط در حافظه استفاده می‌شود تا `mobile_activate_authenticated.php` دستگاه دارای کلید عمومی P-256 را به `mobile_users.inspector_ref` همان کاربر پیوند دهد.
3. مدیر از طریق `mobile_admin_devices.php` دستگاه را تأیید می‌کند.
4. اپ، وضعیت را با درخواست امضاشده از `mobile_activate_status.php` می‌خواند و `device_token` را با AES-GCM در Android Keystore نگهداری می‌کند.
5. در صورت فعال‌کردن اثرانگشت، توکن با کلید وابسته به `BIOMETRIC_STRONG` دوباره رمز می‌شود و فقط پس از `BiometricPrompt` آزاد خواهد شد.
6. نشست موبایل از `mobile_session.php` با امضای P-256 و توکن دستگاه ساخته می‌شود و تنها ۳۰ دقیقه اعتبار دارد.

## امکانات موجود

- ورود واقعی با نام کاربری و رمز عبور، ثبت دستگاه و دریافت تأیید مدیر
- ورود مجدد با اثرانگشت سخت‌افزاری قوی پس از فعال‌سازی اختیاری
- دریافت مأموریت‌های مجاز و فیلترشده از `mobile_sync.php`
- فهرست مأموریت‌ها، نمایش چک‌لیست و امتیازدهی ۰ تا ۱۰۰
- ذخیره رمزنگاری‌شده اطلاعات همگام‌سازی و پیش‌نویس‌ها برای استفاده بدون اینترنت
- انتخاب عکس یا PDF و ارسال پیوست‌های سؤال به `mobile_upload.php`
- کنترل کیفیت سمت کاربر و ارسال نهایی با `mobile_submit.php` و دریافت کد رسید

## محدودیت‌های مهم مرحله ۲

- این نسخه **پیش‌نمایش اجرایی سورس (MVP)** است؛ هنوز Room/WorkManager، همگام‌سازی خودکار صف آفلاین، ثبت دوربین داخلی، مدیریت تعارض و اطلاع‌رسانی Push ندارد. ارسال نهایی فقط با اینترنت و **اقدام صریح کاربر** انجام می‌شود.
- ثبت دستگاه جدید همچنان منوط به تأیید مدیر است؛ ورود با رمز عبور به معنای فعال‌سازی خودکار دستگاه نیست.
- اگر در `mobile_users` نگاشت دقیق `inspector_ref` به شناسه پروفایل بازرس وجود نداشته باشد، خطای `mobile_account_mapping_required` برمی‌گردد و مدیر باید در پنل نگاشت را اصلاح کند.
- فعلاً فقط نقش `inspector` پوشش داده شده است؛ حساب فرماندار و مدیریت گزارش در وب می‌ماند.
- اگر دستور `Clear storage` اجرا شود، کلید Keystore و پیش‌نویس‌های محلی ممکن است از دست بروند. نسخه پشتیبان اطلاعات محلی توسط این اپ غیرفعال است.
- برای ارسال سؤال‌های بحرانی، مستند لازم است و الزامات سخت‌گیرانه سمت سرور (محدوده مأموریت، محدودیت تاریخ، بررسی سؤال‌ها) همچنان برقرارند.
- افزودن امکانات حرفه‌ای بعدی، تست API روی MySQL staging، اجرای instrumented test روی گوشی و بررسی حریم خصوصی/حذف داده ضروری است.


## نسخه ۰.۵.۰ — بازطراحی Native

این نسخه از رابط کاملاً بومی Android View استفاده می‌کند و هیچ WebView یا صفحه وبی در اپلیکیشن ندارد. سربرگ عریض وب حذف شده و با نوار ابزار سازمانی فشرده، نشان رسمی، صفحه ورود کارت‌محور، داشبورد مأموریت‌ها و ناوبری پایین Native جایگزین شده است.


## نسخه ۰.۵.۰ — رابط کاربری Native سازمانی

- نوار ابزار ثابت و فشرده Android به‌جای بنر عریض شبیه وب
- صفحه ورود بومی با فیلدهای Material و کارت هویت سازمانی
- داشبورد مأموریت‌ها با کارت‌های آماری و ناوبری پایین Native
- هیچ WebView یا صفحه وبی در رابط کاربری استفاده نشده است
- API، ذخیره آفلاین، تأیید دستگاه و بیومتریک حفظ شده‌اند

برای جزئیات نصب، فایل `INSTALL_V4_2_FA.md` را در ریشه بسته بخوانید.

## نسخه ۴.۹.۰ — کارتابل سربازرس

این نسخه امکان تعیین یک بازرس موجود به‌عنوان سربازرس را بدون ساخت حساب دوم فراهم می‌کند. سرور شناسه حساب موبایل بازرس منتخب را ثبت می‌کند و اپ پس از همگام‌سازی، تب «سربازرس» را فقط برای همان حساب نشان می‌دهد. برای جزئیات نصب و گردش تأیید، فایل `README_V4_9_0_FA.md` در ریشه بسته را ببینید.


## نسخه 4.10.0 — مدیریت دسترسی ادارات

- تب «ادارات مجاز من» در ناوبری پایین اپ افزوده شد.
- فهرست اداره‌ها از `authorized_organizations` در پاسخ `mobile_sync.php` دریافت می‌شود؛ این فهرست فقط اداره‌های مجاز طبق سیاست سرور را نمایش می‌دهد.
- تغییر دسترسی فقط از پنل مدیریت انجام می‌شود؛ اپ موبایل صرفاً دسترسی مؤثر را نمایش می‌دهد.
- همگام‌سازی، ارسال مستند و ارسال گزارش در API نیز مجاز بودن اداره را کنترل می‌کنند؛ نمایش فهرست به‌تنهایی مرز امنیتی محسوب نمی‌شود.
- برای ساخت APK در GitHub Actions، متغیر مخزن `BAZR_API_BASE_URL` را با نشانی کامل HTTPS API که با `/` پایان می‌یابد تنظیم کنید.


## نسخه ۴.۱۱.۰ — صفحه‌بندی بر اساس شاخص‌های بازرسی

- هر شاخص (`sections[]`) یک صفحه مستقل در اپلیکیشن Native دارد.
- همه آیتم‌های هر شاخص با اسکرول عمودی در همان صفحه نمایش داده می‌شوند.
- ترتیب شاخص‌ها از `checklistSnapshot.sections` و ارتباط سؤال‌ها از `sectionId` خوانده می‌شود؛ شناسه سؤال‌ها و بندهای ۸۶گانه تغییر نمی‌کنند.
- پیشرفت کل مأموریت و پیشرفت شاخص جاری جداگانه نمایش داده می‌شود.
- نوار ثابت پایین صفحه شامل «شاخص قبلی»، «امضا» و «شاخص بعدی / مرور گزارش» است.
- دکمه امضا از هر شاخص در دسترس است؛ بندهای بدون امتیاز در مرحله مرور و هشدار پیش از امضا نمایش داده می‌شوند و تکمیل همه بندها اجباری نیست.
- پاسخ‌ها، توضیحات، مستندات، صف ارسال، گردش سربازرس و PDFها در این بازطراحی از همان مدل داده و مسیرهای قبلی استفاده می‌کنند.

**محدودیت تأیید:** سورس در این محیط ویرایش و بررسی ساختاری شده است؛ به‌دلیل در دسترس نبودن Android SDK و Gradle در محیط اجرا، APK در اینجا کامپایل یا روی گوشی واقعی آزمایش نشده است. برای تأیید نهایی، GitHub Actions باید build موفق بدهد و روی دستگاه دوربین، گالری، ذخیره خودکار، رفت‌وبرگشت بین شاخص‌ها و امضای ناقص آزمایش شود.
